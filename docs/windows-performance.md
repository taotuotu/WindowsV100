# Windows / V100 性能记录

这里汇总历史本机测量、运行元数据及2026-10-02使用者配置反馈；本轮没有运行新基准。原始日志与任务内容不进入公开包。速率来自不同请求与配置时，不能当成受控比较。

## 当前默认配置与使用者反馈

2026-10-02 使用者报告其任务中 MTP 草稿长度6最快，预填充分块2048时需要将上下文降至143600
避免 OOM。Windows启动器、原生服务默认值与发行manifest采用143600 / BF16 KV / MTP6 /
prefill2048；本机配置相同。各长度档位的输入、接受率、速率与重复次数尚未归档，
因此不把“6最快”作为所有任务或其它GPU的受控结论。以下MTP3/prefill512数据保留为历史记录。

### 长上下文与 MTP 档位

**长上下文性能声明：** 按本机使用观察，实际上下文占用越大，较大 MTP 草稿长度相对于较小草稿长度的速度表现越差，长上下文下可能更慢。MTP6 的默认选择来自此前任务反馈；长上下文应结合实际输出吞吐选择较小档位。

这里的上下文占用指实际处理的输入与聊天历史及对应 KV 占用，仅提高配置中的容量上限不等于实际上下文变长。该声明属于使用者运行反馈；具体差异仍受任务、草稿接受率与上下文长度影响，尚未形成各长度与档位组合的受控曲线。

## 环境与口径

- Windows x64；Tesla PG500-216 / V100 32 GiB、SM70、TCC；CUDA 12.9 / MSVC 19.44。
- NInfer 基线 `geoffwatts/ninfer-v100@b37d0dd` 加 Windows 移植；Qwen3.8-27B mixed NVFP4/FP8 v2，固定 SHA 见 [来源记录](provenance.md)。
- learned MTP3、optimized proposal head；服务 prefill chunk 512、单活动请求。各表单独注明 KV。
- CLI decode：生成 token 数减首 token，除以 Program 解码耗时。HTTP/网页 decode：同样 token 数除以首到末输出提交的墙钟耗时。
- prefill、decode、请求总时间与启动时间分别计量。服务端 TTFT 不包括浏览器网络开销；网页 TTFT 包括。

## 已记录的完整配置对比

| 任务 | NInfer NVFP4/FP8 + INT8 KV + MTP3 | llama.cpp IQ3_S + FP16 KV + MTP3 |
|---|---:|---:|
| 短任务 A | 约 70 tok/s | 约 44 tok/s |
| 短任务 B | 约 72 tok/s | 约 48 tok/s |
| 短任务 C | 约 96 tok/s | 约 65 tok/s |
| 实际 5118-token 输入 | 约 63 tok/s | 约 41 tok/s |

这些是引擎、权重、KV、proposal head 等共同变化的配置对比，不隔离原创内核贡献；不同量化的输出与质量也不等价。Unicode 复制曾正确，大整数任务两侧都失败，不能据此证明质量等价。

同一个 NInfer 模型、5118-token 输入、256 输出上限、8192 容量、MTP3、greedy / seed123 / prefill512，BF16 KV 三次为 **63.852 / 63.883 / 63.886 tok/s**，平均 **63.87**；历史 INT8 两次平均 63.25。BF16 MTP 接受率 56.74%，INT8 54.86%，这个差异不能归因为独立 KV 带宽成本，也不能外推到 15 万 token 实际输入。

真实 HTTP 调用的不同输出观察到约 45.6–138.1 tok/s，MTP 接受率约 34.9%–92.8%。它说明工作负载会显著改变速度；不作为固定速度承诺或受控基准。

## 接下来值得优化的地方

### 冷输入的预填充

已存在的约13.3K冷输入记录：prefill约16.55秒，其中 `host_exposed` 约7.18秒、`device_wait_exposed` 约9.37秒。主机侧计时约占43.4%，其它相似调用约43.4%–43.6%；CUDA API 时间可能包含驱动与提交等待，不能把它全部解释为 CPU 运算。

后续受控测量可将当前 prefill2048 与512 / 1024比较，固定模型、KV、MTP、输入和输出设置，同时记录内存预算、TTFT、主机时间与 GPU 等待。较大 chunk 会增加预留显存，因此当前容量采用143600；旧153600配置的余量不能外推到新参数。当前记录不足以承诺某个提速百分比。

### MTP 窗口与接受率

K=6 是当前按使用者反馈选择的默认。后续受控比较 K=1..7 时，需同时记录 accepted / drafted、实际输出量、阶段耗时和任务完成情况；不同接受率的请求不能直接排行。上游 context lookup 延长到第4–15位的接受计数已在真实调用出现，但它只在复制/重复内容且 proposal 一致时帮助，不能推导所有任务都能到200 tok/s。

### 已有缓存和 CUDA Graphs

前缀缓存已经提供明确命中；增加缓存槽要先看到淘汰压力，因为额外 Device State 每份约146.82 MiB，Host State 每份同等 pinned 内存。解码 CUDA Graphs 已启用，旧长请求的主机解码开销相对 GPU 等待很小；现有证据更支持优先处理冷 prefill。

超长实际输入下 BF16 与 INT8/FP8 KV 的速度及质量仍需独立比较。容量成功不能代替这项测量。

## 证据限制

本地没有重新执行完整上游 CUDA Op 独立 oracle、全协议测试或浏览器交互测试。网页源码语法编译、Windows 服务构建、正常启动预热、只读 health / model-info / 页面提供已有记录；这些不建立全部交互与数值正确性结论。本轮不改变 GPU 数值内核，也没有主动发生成测试请求。

上游 [Linux V100 记录](v100.md) 中的合成续写约219 tok/s和 [RTX5090 记录](performance.md) 保留各自原环境与方法；不得作为这个 Windows 发行版的一般性能宣传。
