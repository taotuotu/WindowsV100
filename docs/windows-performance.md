# Windows / V100 性能记录

这里汇总历史本机测量、运行元数据、使用者反馈及2026-10-03视觉与回复尾部实验。原始日志与任务内容不进入公开包。速率来自不同请求与配置时，不能当成受控比较。

## 当前默认配置与使用者反馈

2026-10-02 使用者报告其任务中 MTP 草稿长度6最快，预填充分块2048时需要将上下文降至143600
避免 OOM。Windows启动器、原生服务默认值与发行manifest采用143600 / BF16 KV / MTP6 /
prefill2048。本机后续另用246000 / INT8 KV / MTP3 / prefill2048 / Vision开启的个人配置。
各长度档位的输入、接受率、速率与重复次数尚未归档，
因此不把“6最快”作为所有任务或其它GPU的受控结论。以下MTP3/prefill512数据保留为历史记录。

### 长上下文与 MTP 档位

**长上下文性能声明：** 按本机使用观察，实际上下文占用越大，较大 MTP 草稿长度相对于较小草稿长度的速度表现越差，长上下文下可能更慢。MTP6 的默认选择来自此前任务反馈；长上下文应结合实际输出吞吐选择较小档位。

这里的上下文占用指实际处理的输入与聊天历史及对应 KV 占用，仅提高配置中的容量上限不等于实际上下文变长。该声明属于使用者运行反馈；具体差异仍受任务、草稿接受率与上下文长度影响，尚未形成各长度与档位组合的受控曲线。

## 环境与口径

- Windows x64；Tesla PG500-216 / V100 32 GiB、SM70、TCC；CUDA 12.9 / MSVC 19.44。
- NInfer 基线 `geoffwatts/ninfer-v100@b37d0dd` 加 Windows 移植；Qwen3.8-27B mixed NVFP4/FP8 v2，固定 SHA 见 [来源记录](provenance.md)。
- learned MTP3、optimized proposal head；服务 prefill chunk 512、单活动请求。各表单独注明 KV。
- CLI decode：生成 token 数减首 token，除以 Program 解码耗时。HTTP/网页 decode：同样 token 数除以首到末输出提交的墙钟耗时。
- prefill、decode、请求总时间与启动时间分别计量。服务端 TTFT 不包括浏览器网络开销；网页 TTFT 包括。

上述任务报告时服务为 v2 模型、BF16 KV、MTP3、prefill512、容量153600。各任务的输入长度、输出 token 数、重复次数与日志定位尚未完整归档，因此这组作为日常使用反馈，不用来作受控跨引擎排名。语言差距可能涉及 tokenizer 与草稿接受率，现有报告没有隔离其原因。

## 已记录的完整配置对比

| 任务 | NInfer NVFP4/FP8 + INT8 KV + MTP3 | llama.cpp IQ3_S + FP16 KV + MTP3 |
|---|---:|---:|
| 短任务 A | 约 70 tok/s | 约 44 tok/s |
| 短任务 B | 约 72 tok/s | 约 48 tok/s |
| 短任务 C | 约 96 tok/s | 约 65 tok/s |
| 实际 5118-token 输入 | 约 63 tok/s | 约 41 tok/s |

这些是引擎、权重、KV、proposal head 等共同变化的配置对比，不隔离原创内核贡献；不同量化的输出与质量也不等价。Unicode 复制曾正确，大整数任务两侧都失败，不能据此证明质量等价。

同一个 NInfer 模型、5118-token 输入、256 输出上限、8192 容量、MTP3、greedy / seed123 / prefill512，BF16 KV 三次为 **63.852 / 63.883 / 63.886 tok/s**，平均 **63.87**；历史 INT8 两次平均 63.25。BF16 MTP 接受率 56.74%，INT8 54.86%，这个差异不能归因为独立 KV 带宽成本，也不能外推到 15 万 token 实际输入。

真实 HTTP 调用的不同输出观察到约 45.6–138.1 tok/s，MTP 接受率约 34.9%–92.8%。它说明工作负载会显著改变速度；不作为固定速度承诺或受控基准。

## 容量与启动

### 磁盘续接的短请求检查（2026-10-02）

同一 V100、固定 v2 NVFP4 artifact，INT8 KV、MTP3、prefill2048、容量246000、Vision开启；请求为纯文本、greedy、关闭思考并保留历史模板。连续两轮短请求中，第二轮输入55 token、命中34、实际计算21；保存两份完整Engine归档后服务仍可用，磁盘保存失败数为0。重启后回传同一会话的完整历史：输入91、命中70、实际计算21，从磁盘恢复935240136字节，随后再次保存成功。它验证正常续接及重启恢复，不是输出速度基准或满容量稳定性测试。

最终构建另查两轮自然 stop-token 结束的短回答：第一轮输入20、输出4；第二轮输入43、输出2、命中23、实际计算20。上一轮回答进入了复用前缀；两轮落盘成功，Engine保持可用，保存失败数为0。再次重启后的第三轮输入64、命中44、实际计算20，恢复622733080字节并保存成功。

独立会话的 SSE 客户端收到11个字符后约404ms中断；服务端提交解码计数增加14，安全快照保存成功且下一轮可生成。客户端只回传可见部分时，下一轮62个输入token命中24、实际计算38，回退到较早的 response-replay checkpoint。这个检查验证断线后的状态保存与服务可用性，也显示任意半截回答不能保证全量命中；未测试长上下文、BF16/FP8或图像输入的磁盘续接。

此前关闭 context cache 的容量分配检查：

| KV / prefill chunk | 成功分配 | 未成功 |
|---|---:|---:|
| BF16 / 1024 | 160000 | 163712 |
| BF16 / 512 | 163712 | 163713 |
| INT8 / 512 | 262144 | 模型上限约束更大容量 |

这些使用短提示词，仅说明容量分配和短生成，不表示已经输入该长度。实际缓存开启的 153600 / BF16 / MTP3 服务启动快照约占 31923 MiB，剩余704 MiB；不是峰值或满上下文稳定性结论。当前公共启动器默认143600 / MTP6 / prefill2048；上述容量数据来自旧配置。

`/ui/model-info` 返回 `vision_enabled=true`，网页和健康状态可读。

## 冷输入 Prefill 实验（2026-10-02）

本次测量完整 public Engine 路径的绝对输入吞吐。每轮从仓库固定
`bench/fixtures/bench_corpus.ids` 取8192或16384个token，关闭前缀复用，请求一个输出token
以执行Prefill；不进入HTTP、磁盘会话或聊天模板处理。每个长度先预热一次，再测三次。
模型与GPU同上；固定INT8 KV、MTP3、optimized proposal head、容量246000、prefill2048。
Windows文字benchmark关闭Vision；不能将本表当作Vision开启的服务端首字时间。
基线为Windows源码 `e2d06fa6`，保持同一个container-v2 artifact与固定语料。
复现命令见 [bench指南](../bench/README.md)。

尝试的实现包括宽FP8投影融合反量化与MMA、CUTLASS分块，以及FP8权重向量化转换。
融合MMA原型的8192-token吞吐约720 tok/s，比基线慢约31%，已撤回。
128×64及256×128的FP8 CUTLASS分块也未得到整体收益，保留原128×128分块。
向量化转换每线程处理八个FP8码，保持逐值解码、FP16舍入、FP32累加和BF16输出边界。

| 输入长度 | 基线首跑 tok/s ±标准差 | 基线复跑 | FP8 flat向量转换首跑 | FP8 flat向量转换复跑 |
|---|---:|---:|---:|---:|
| 8192 | 1049.65 ±4.03 | 1049.61 ±2.67 | 1059.37 ±3.74 | 1047.56 ±2.90 |
| 16384 | 975.83 ±4.32 | 975.30 ±4.86 | 984.25 ±5.10 | 969.07 ±14.73 |

首轮约0.9%的提升在复跑中没有复现，不能宣称稳定收益。改用逐行二维网格、
避免线程内64位运行期整除后，单轮三次平均为1061.21 ±3.73 / 985.55 ±4.65 tok/s。
NVFP4 QPN扁平网格的MLP微基准有改善，但整模型组合结果1058.44 / 984.80 tok/s
没有显示额外收益，撤回该NVFP4网格改动。

数值检查直接调用公开
`attn_input_proj`、`gdn_input_proj`及FP8 `linear_add`，使用独立CPU FP64点积与存储权重解码
oracle；覆盖真实投影形状、native/QPN布局、宽T分派边界和部分尾块，通过。
另外扩展NVFP4 `linear_add`与`linear_swiglu`的T33/64/128 native/QPN检查。
它发现原宽输入SwiGLU把gate/up先舍入BF16再组合，实际4.59375对独立FP64参考4.55671
未通过原A16容差。最终实现让CUTLASS保留FP32投影，并按每token的gate/up两半读取，
在FP32完成SiLU乘法后只舍入一次BF16；容差未放宽。
FP8三项与NVFP4两项独立oracle均通过；未将未受影响的算子全套检查作为本次证据。
该数学修复会改变后续隐状态，旧磁盘续接按新的math revision隔离，详见
[Windows缓存说明](windows-v100.md)。

修复后的最终构建保持逐行FP8向量转换，撤回NVFP4扁平网格。三次平均：

| 输入长度 | 最终首跑 tok/s ±标准差 | 最终复跑 | 两轮六次平均 | 基线两轮六次平均 |
|---|---:|---:|---:|---:|
| 8192 | 1057.78 ±3.48 | 1051.09 ±2.96 | 1054.44 ±4.67 | 1049.63 ±3.06 |
| 16384 | 982.46 ±4.42 | 979.04 ±3.97 | 980.75 ±4.20 | 975.56 ±4.12 |

最终构建的SwiGLU中间精度已修正，基线有上述数值缺陷，因此这不是输出数值完全等价的
性能对比。两轮均值差约0.46% / 0.53%，本轮没有取得明显的输入吞吐提升；
这些小变化不能作为普遍或固定提速承诺。最终构建保留低风险FP8向量转换和已验证的数学修复。

最终Windows服务在独立的短目录检查磁盘续接（Vision开启、其余配置同本机个人配置）：
两轮自然stop的第二轮37输入、18命中，保存失败为0；重启后第三轮57输入、38命中，
导入622732822字节并再次保存成功。此前深层测试目录遇到文件打开失败，改用短目录后通过；
这不建立任意Windows长路径可用的结论。没有向本机原会话目录写入测试会话。

Nsight Systems本机报告只采到CPU NVTX范围，没有CUDA kernel/API时间线。
因此这里不按这些范围排序GPU瓶颈，也不把主机等待时间等同于GPU活跃时间。

## 视觉与回复尾部优化（2026-10-03）

同一张 V100、固定 v2 artifact、CUDA 12.9 / MSVC 19.44，基线为源码 `2eaa272b`。
以下是本次改动前后的实际 HTTP 请求，不是单个 attention kernel 微基准。

### 完整视觉编码和首字

两侧固定容量8192、INT8 KV、MTP3、prefill2048、Vision开启、单请求；冷会话、
greedy、关闭思考、输出上限32。输入为相同的合成 PNG 网格图和简短描述请求，
分别为1280×960与2048×2048；每个形状每侧测一次，服务就绪后再提交请求。
图像解码、resize和patch数量保持一致，未用降低分辨率取得收益。

| 图像 / raw patches / merged tokens | 基线完整视觉编码 | 本次完整视觉编码 | 耗时减少 | 基线服务端首字 | 本次服务端首字 |
|---|---:|---:|---:|---:|---:|
| 1280×960 / 4800 / 1200 | 4.575秒 | 1.272秒 | 72.2% | 5.910秒 | 2.609秒 |
| 2048×2048 / 16384 / 4096 | 45.345秒 | 6.292秒 | 86.1% | 49.389秒 | 10.560秒 |

视觉编码的加速约为3.60倍与7.21倍；完整首字耗时分别减少55.8%与78.6%。
收益来自SM70单段、D72/H16的非因果attention快路径：复用已固定的llama.cpp Volta
FlashMMA实现，使用调用方workspace，并以约1024 keys的分片和FP32 fixup限制累加误差。
快路径范围为1024–16384 raw patches；其它形状、多段或更大的图像回退已有实现。
它没有做稀疏attention或输入压缩，但私有浮点计算方式改变，不能承诺答案逐位相同。

公开BF16输入直接对独立CPU FP64 dense attention oracle检查，未放宽原容差：
短形状、1024/1025边界、真实4800/16384形状的代表性query、以及多段隔离均通过。
大形状覆盖所有heads与所有keys；测得relative L2约0.00188–0.00208，低于0.0025上限。

### 末段输出到 SSE 完成

两侧固定容量65536、INT8 KV、MTP3、prefill2048、Vision开启；相同48017-token
合成文本输入，greedy、关闭思考，回答自然结束为2个token。每侧测一次。
旧路径在最后一段输出后同步写完整磁盘快照；本次先捕获不可变host归档，
再在后台计算checksum和原子提交。测量为客户端最后一段内容到 `[DONE]`，
与decode tok/s和服务端生成阶段总时间分别计量。

| 阶段 | 基线 | 本次 | 耗时减少 |
|---|---:|---:|---:|
| 最后一段输出到 `[DONE]` | 2.860秒 | 1.327秒 | 53.6% |

本次仍需等待稳定状态从GPU捕获到host，48K请求约1.3秒，并非零等待。
随后立刻提交下一轮，48036输入token命中48018、重算18，服务端首字约0.357秒，
没有因后台写盘收到429。快照捕获复用pinned staging并批量传输device KV pages；
Core原始字节传输与长度拒绝检查通过。归档格式与本次之前的math revision保持一致。

在保存运行中正常关闭服务后重启，同会话48036输入命中48029、只计算7；
从磁盘导入2348637280字节，保存失败数为0。另在48K历史中收到32个字符后断开SSE，
下一轮回传可见的半截回答：48080输入命中48046、重算34，仍能正常结束并保存。
这验证断线续接可用，不保证任意截断位置全量命中。后台保存期间执行清缓存，
最终磁盘字节/会话数/队列均为0，旧任务被取消且没有恢复已清除的head。
此前出错的深层测试目录也通过了实际保存与重启恢复：导入613685478字节图像会话归档，
4116输入命中4109、重算7，保存失败为0；Windows文件操作现使用扩展绝对路径。

`[DONE]` 表示host捕获完成，最新一代可能仍在后台写盘。正常关闭会排空保存队列；
强杀或断电仍可能只恢复上一代完整提交。两份长上下文归档可能增加系统内存峰值，
具体预算与操作说明见 [Windows缓存说明](windows-v100.md)。

## 接下来值得优化的地方

### 冷输入的预填充

已存在的约13.3K冷输入记录：prefill约16.55秒，其中 `host_exposed` 约7.18秒、`device_wait_exposed` 约9.37秒。主机侧计时约占43.4%，其它相似调用约43.4%–43.6%；CUDA API 时间可能包含驱动与提交等待，不能把它全部解释为 CPU 运算。

后续受控测量可将当前 prefill2048 与512 / 1024比较，固定模型、KV、MTP、输入和输出设置，同时记录内存预算、TTFT、主机时间与 GPU 等待。较大 chunk 会增加预留显存，因此当前容量采用143600；旧153600配置的余量不能外推到新参数。当前记录不足以承诺某个提速百分比。

### MTP 窗口与接受率

K=6 是当前按使用者反馈选择的默认。后续受控比较 K=1..7 时，需同时记录 accepted / drafted、实际输出量、阶段耗时和任务完成情况；不同接受率的请求不能直接排行。上游 context lookup 延长到第4–15位的接受计数已在真实调用出现，但它只在复制/重复内容且 proposal 一致时帮助，不能推导所有任务都能到200 tok/s。

### 已有缓存和 CUDA Graphs

前缀缓存已经提供明确命中；增加缓存槽要先看到淘汰压力，因为额外 Device State 每份约146.82 MiB，Host State 每份同等 pinned 内存。解码 CUDA Graphs 已启用，旧长请求的主机解码开销相对 GPU 等待很小；现有证据更支持优先处理冷 prefill。

超长实际输入下 BF16 与 INT8/FP8 KV 的速度及质量仍需独立比较。容量成功不能代替这项测量。

## 证据限制

本地没有重新执行完整上游 CUDA Op 独立 oracle、全协议测试或浏览器交互测试。网页源码语法编译、Windows 服务构建、正常启动预热、只读 health / model-info / 页面提供已有记录；这些不建立全部交互与数值正确性结论。磁盘续接功能另有上述经用户授权的本地短请求检查；本次Prefill实验的局部CUDA检查与口径见上节。

上游 [Linux V100 记录](v100.md) 中的合成续写约219 tok/s和 [RTX5090 记录](performance.md) 保留各自原环境与方法；不得作为这个 Windows 发行版的一般性能宣传。
